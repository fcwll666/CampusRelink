# 发布指南

当前发布版本为 **1.0.3**，程序集和文件版本为 **1.0.3.0**，对应 Git 标签 **`v1.0.3`**。以下描述仓库中现有脚本与工作流的行为，不表示该仓库的线上 CI 已运行或通过。

## 本地核验与打包

在 Windows x64、.NET Framework 4.8 和 Windows PowerShell 5.1 环境，从仓库根目录执行：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\Package.ps1
```

脚本默认先运行 `Test.ps1`，再运行 `build.ps1`，成功后生成：

- `dist\CampusRelink-1.0.3-win-x64.zip`
- `dist\CampusRelink-1.0.3-source.zip`
- `dist\SHA256SUMS`

测试当前为五套入口、138 个用例的离线假环境检查，包含少量系统只读查询，不等于真实校园网验证。打包不启动应用正常入口，不发送真实认证请求，不修改 Wi-Fi、系统代理或自启任务。真实校园网络验证由维护者自行决定，并应与自动化结果分开记录。

仅在明确复用已验证的同版本 EXE 时使用 `-SkipValidation`；它会跳过本次测试和编译，不应作为日常发布命令。脚本会检查 EXE 文件版本，并保留其他版本的 ZIP，但 `SHA256SUMS` 只列出本次 1.0.3 的两个 ZIP。

## 检查待发布文件

1. 阅读 `CHANGELOG.md`、`README.md`、`NOTICE.md` 和 `LICENSE`，核对版本、适用校园、协议范围和署名。任何未验证场景均须如实说明。
2. 检查本次 `artifacts\tests\<运行标识>\results.json` / `results.csv`，确认五套测试完成且全部通过；保留对应运行记录，不将它们加入发布 ZIP。
3. 查看两个 ZIP 的实际目录。二进制包包含 EXE、简明 README，以及使用、排查、开发、发布、协作和许可文档，共 14 个文件，不包含源码或测试产物；源码包按 `Package.ps1` 的明确清单收集。新增社区文件、文档或素材需有意加入清单。禁止递归打包整个工作目录。
4. 确认无应用数据、凭据、个人路径截图、开发机 SSID 列表、日志、诊断包、代理备份、自启任务导出、私钥及构建暂存文件。
5. 使用 `Get-FileHash -Algorithm SHA256` 核对两个 ZIP 与本批次 `SHA256SUMS`。发布的 EXE 未签名；不要把哈希描述为发布者签名。

## GitHub 工作流与草稿 Release

现有 `.github/workflows/build.yml` 在 `main` / `master` 分支推送、PR、`v*` 标签推送或手动触发时运行 Windows 构建。构建任务执行 `Package.ps1`，上传测试报告和发布包。

维护者核验待发布提交后，才创建并推送 `v1.0.3` 标签。标签触发的发布任务依赖构建成功，下载该次构建产物，并通过 GitHub CLI 创建 **Draft Release**。工作流明确拒绝其他版本标签；发布下一版本前，应同步更新源码版本、构建检查、打包文件名、工作流和文档，而不是直接推送新版本号。

标签推送后的线上状态必须查看该次 Actions 运行确认，不能由本地测试推断。若运行失败，先排查失败步骤与测试报告；不要用来源不明或未验证的本地产物替换后声称 CI 已通过。

## 人工发布

发布草稿前，再检查目标标签和提交、版本说明、两个 ZIP 与 `SHA256SUMS` 是否齐全，并核对附件哈希。发布说明应包含适用范围、未签名状态、默认 HTTP 认证接口的传输边界及迁移注意事项，避免声称全面校园兼容。

GitHub 工作流创建的草稿需要维护者审阅并手动发布。不要把创建草稿等同于已经公开发布，也不要为重跑自动删除或移动已发布标签。已公开的包若需要修改，采用新的补丁版本，并保留变更记录。
